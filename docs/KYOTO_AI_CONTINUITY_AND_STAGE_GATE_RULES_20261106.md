## 既定の工程順
P1 予測用データの取得・欠落と時点の証明
→ P2 勝馬・連対馬の特徴自動発見と汎化確認
→ P3 複数確率モデルの比較・較正
→ P4 馬連・枠連の発走前オッズと期待値
→ P5 推奨レース・買い目・資金配分・見送りの最適化
→ P6 発走前証拠固定、仮想投資、公式結果の自動採点
→ P7 新旧モデル同条件検証、改善時のみ採用
→ P8 スマートフォン向け本番統合。

準備作業が並行できる場合も、未完了の前提を通過したと偽って次段階の性能実証を宣言しない。

## 新しいチャットの必須開始手順
1. 最初に上記の正本要件・工程・直近チェックポイントを確認する。
2. **成功済みの検証を繰り返さず**、最新の確定レシートとGitHub Actionsの成否から現在地を復元する。
3. 取りこぼした要件や未完了の前提を明示し、原則として現在進行中のP1の次の未完了工程から着手する。
4. 実行ごとに原本のSHA-256、日時、成功・失敗、完了ゲート、次回再開位置を保存する。バッチが途中停止したら再開レシートを使い、重複取得・重複登録を避ける。
5. ユーザーに同じ方針を繰り返し確認させない。通常作業は既定方針の範囲で進める。

## 例外として工程停止・変更が正当化される条件
- 重大なデータ誤り、未来情報の混入、出走取消の取り違え等が見つかった場合。
- JRA等のサービス利用条件、法令、アクセス制限、安全性、無料枠、認証・環境に重大な障害がある場合。
- 公式原本、時点証明、保存・再開証拠の不整合があり、このまま次へ進むと誤った予測やデータ破損の危険がある場合。
- ユーザーが明示的に工程変更・優先順位変更を指示した場合。

例外が生じた場合は、**何を検出したか、影響範囲、停止が必要な理由、再開に必要な条件**を明示する。前提が復旧すれば元の工程順へ戻る。思いつきによる設計変更や、単なるチャット移行は例外に含まれない。

## 保護対象
`main/app.py`、本番Turso、公開済み予測モデル、実馬券購入記録は、明示的な承認なしに変更しない。個人趣味の開発は業務用Work/Codexと分離し、追加費用は原則0円。過去に確定したアルゴリズム要件を勝手に削除・矮小化しない。

**この継続規則を、チャット間の作業継続における原則とする。** 実行環境がGitHubを参照できない場合は、進捗を推測せず、保存済み正本と実証の可否を明示する。
