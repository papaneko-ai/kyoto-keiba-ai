# 取得障害から次回修正までの恒久運用原則

目的は取得件数を報告することではなく、実際の失敗から原因を特定し、次の開催までに再現・修正・再発防止を実証可能にすること。

- 成功したActionsジョブでもデータ不足を診断する。外部タイマー、手動、ネイティブ起動を同じ実行ID・日付・ワークフローで管理する。
- 取得終了後に独立の診断workflowが既存暗号化原本を認証して読み、失敗段階、既知の直接障害シグネチャ、未証明の原因、上流停止による下流欠落、修正方向・必要な回帰試験を分離する。生データ、URLトークン、秘密を公開しない。
- 診断結果はreport.jsonとSHA256、元実行ID・原本ハッシュ・取得時刻が分かる範囲で保存し、Issue #141へ安全な作業リストを恒久追記する。アーカイブ欠落は原因未確定であり、通信失敗と同一視しない。
- 原因確定の条件：保存された実原本または実行証拠、最小再現、同一原因の他箇所探索。修正終了の条件：隔離候補、該当失敗を再現する回帰試験、既存保護条件、全体回帰、独立の本番再照合。未証明項目は閉じない。
- 次回開始前に未処理の作業リストを先に確認し、既存の成功を再利用する。原因に基づく修正候補は証拠と試験を伴って採用する。診断だけで自動コード変更や不正な取得・アクセス制限回避は行わない。
- 現在の自動起動登録は2026-11-28/29の5つの取得ワークフロー。次開催のスケジュール作成時に登録と対象日を更新して試験する。未登録の取得器を運用開始しない。
- 完全な原因確定や未知障害の修復保証ではない。診断の欠落・runner全損・API障害自体も未解決として記録し、保存や検証の失敗を成功にしない。

既存の固定取得枠、外部タイマー、Turso、Secrets、PC/SP・午後・結果取得pinは変更しない。今回の機能は元の取得器を止めない独立診断。
