## 2. 既存研究成果の確認が新規実装の前提条件
新しい設計・コード・テスト・資料を作る前に、毎回、**最新のGitHub開発ブランチHEAD**で次を実読・照合する。
1. 本規程および進捗合意 `docs/KYOTO_AI_PRE_DATA_READINESS_PROGRESS_AGREEMENT_20261113.md`、既存の移行・復旧パック、直近の成功CI/失敗CI、保存済み原本・Artifactの根拠と最新版。
2. 既存の研究要件の正本 `docs/KYOTO_AI_ALGORITHM_REQUIREMENTS_REGISTER_v1_20261106.md`、`docs/KYOTO_AI_ALGORITHM_AND_EXECUTION_ROADMAP_20261106.md`、`docs/KYOTO_AI_HYBRID_SELF_EVOLUTION_MODEL_ARCHITECTURE_20261112.md`、固定16評価台帳 `docs/diagnostics/kyoto_predata_readiness_rubric_v1.json`。
3. `docs/diagnostics/kyoto_feature_reuse_inventory_v1.json` と `docs/diagnostics/kyoto_change_intent_v1.json`、`diagnostics/kyoto_development_preflight.py` に登録済みの機能・実装済/部分実装/設計のみの区別。関連するソースファイル、テスト、過去の保存レシート、既知の不具合、コミット、CI結果を直接調べる。
4. 同じ用途の既存部品・テストがあるか、対象のアルゴリズム/要件/受入条件に機能単位で照合する。**要件台帳の旧版に記された「未実装」を現在の未実装と決めつけない**。新しいHEADのコード・試験・証拠を優先する。

その結果を毎作業の内部チェックとして **既存機能 → 差分/不具合 → 再利用する部品 → 最小修正 → 必要な新規実装 → 正負/破壊/回帰試験 → 認定・不認定の証拠** の順に整理する。実装済みの同じ機能を別名称で二重に作らない。既存の正常動作を無意味に再実行しない。修正が必要なら根本原因を特定し、既存部品の最小変更と回帰試験を優先する。資料だけの増殖を開発進捗とみなさない。

### 重複防止の分岐
- **REUSE**: 既存機能が正しく動作 → 再利用し不足する証拠だけを補う。
- **REPAIR**: 実装はあるが欠陥/不足 → 根本原因を調べて局所修理・再発防止テストを行う。
- **INTEGRATE**: 単体機能が存在し接続がない → 新モジュールを必要最小限のアダプターに限定し既存コードを呼び出す。
- **NEW**: 先行成果を実読しても同等機能が存在しない場合に限り新規実装する。
- 機能名の違いだけでNEW判定にしない。既存の事前確認器でNEW重複が検出されたら先に止めて見直す。

## 3. セクション停止前の移行警告（恒久）
- 開発担当は会話の長さ、添付・実装履歴の増加、過去結果の追跡負荷、文脈の取り違えリスク、接続ツール/コンテキストの不安定さを能動的に点検する。
- **「チャットが止まってから」ではなく、停止・混乱のおそれが出る前にユーザーへ移行アラートを出す**。ユーザーにセクションごとの再指示を求めない。
- 一律の文字数で限界到達を正確に予知できると主張しない。大きな節目の完了前後と、複数回のコード・CI・長い確認履歴が積み重なる場合を早期警告の目安とする。必要なら節目の途中でも安全なチェックポイントで警告する。
- 移行を提案するときは、**移行先で迷わず再開できる完全移行パックと全文の開始指示**を準備する。必須内容：最新開発HEAD、branch、GitHub Actions Run/Jobの結果・Artifact ID、復元方法、作成済み成果の位置、証拠の有効/未確認区別、固定進捗の前回・今回・増減、既知不具合、未認定項目、保護対象、次に着手すべき具体的手順、今回の合意事項。
- 移行資料は**作成時点の暫定数値を最新の確定値に上書きせず混同しない**。最終RUN SUCCESSまで確認し、次セクションの冒頭で最新HEADとCIを再照合する。途中の資料に古い数値があればその旨と確定済みの新しい数値を明記する。
- **移行してもP工程・要件・過去の成功・禁止事項・16項目基準は不変**。すべての次セクション移行文書に本規程への参照を含める。
